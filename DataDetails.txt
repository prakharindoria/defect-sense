AI Friday Season 2 – Regional Finale
 
Manufacturing Quality Control Defect Detection Agent
 
PROBLEM STATEMENT
 
Manufacturing plants require efficient quality control processes to detect defects early and reduce rework or scrap costs. Manual inspections are labor-intensive and subject to human error, causing inconsistent quality outcomes. Existing automation solutions are often limited to specific defect types and lack integration with production data and feedback loops. An AI multi-agent system that analyzes sensor data and inspection images, integrates with MES systems, and provides real-time defect detection and alerts can significantly enhance quality control effectiveness.
 
Data Considerations:
 
Sensor readings (temperature, vibration, etc.) and high-resolution inspection images; production metadata from MES; historical defect records; moderate to high data volume with real-time streaming; preprocessing includes noise filtering and image normalization; privacy for proprietary production data; synthetic defect datasets with labeled anomalies for development.
 
Consider using synthetic or anonymized data where appropriate. Ensure data quality and relevance to the problem context.
 
SOLUTION EXPECTATIONS
 
A multi-agent AI system featuring agents for sensor/image data ingestion, defect detection using computer vision and pattern recognition, and alert management. Features include a quality control dashboard with real-time defect visualization, trend analysis, and reporting. Integrations with MES APIs enable automated data flow and incident logging. Success metrics focus on detection accuracy, inspection time reduction, and defect rate improvement. Demonstrations include live defect detection scenarios, multi-agent workflow, and comprehensive documentation with test suites.
 
Feel free to explore creative solutions that align with the problem context and objectives.
 
Strongest concept: Quality Twin AI
A multimodal quality-control system that does more than detect a defect. It explains:
 
What is defective, why it happened, what should happen next, and whether similar products are at risk.
 
Most teams will build image detection plus alerts. Your differentiator should be combining inspection images, sensor readings, and production history into one evidence-backed decision.
Winning pitch
 
“Traditional vision systems see defects. Quality Twin understands the production conditions that caused them, recommends corrective action, and learns from operator feedback.”

Recommended five-agent design
1. Data Guardian Agent
Responsibilities:
 
Receives inspection images and sensor streams.
Normalizes images.
Removes noisy sensor readings.
Checks for missing or corrupted data.
Attaches MES metadata such as machine, batch, product, and timestamp.
 
Useful innovation: It can report “Prediction confidence is reduced because vibration data is missing.”
 
2. Vision Inspector Agent
Responsibilities:
 
Detects scratches, cracks, dents, contamination, or other anomalies.
Highlights the defect with a bounding box or heatmap.
Calculates defect type, size, location, and confidence.
 
For a 36-hour prototype, use:
 
A pretrained model or transfer learning.
PatchCore/PaDiM-style anomaly detection if you have mostly “good” images.
YOLO if labeled defect examples are available.
 
Demo value: A live camera or uploaded image immediately displays the defect area.
 
3. Sensor Sentinel Agent
Responsibilities:
 
Detects abnormal temperature, vibration, pressure, or speed.
Compares current readings with the “golden run.”
Calculates sensor anomaly scores.
Detects trends before fixed thresholds are crossed.
 
Example:
 
“Vibration is still within the allowed limit, but it has increased by 24% over the last 15 products.”
 
This is stronger than basic threshold alerts.
 
4. Root-Cause Investigator Agent
Responsibilities:
 
Combines evidence from images, sensors, MES data, and defect history.
Finds correlations between defect types and production conditions.
Returns ranked causes with supporting evidence.
 
Example:
 
Likely cause: tool misalignment — 81% confidenceEvidence: scratches appeared after vibration increased on Machine M-04. Four similar incidents were recorded previously.
 
Use a transparent rules-and-statistics engine rather than claiming that an LLM discovered the cause independently.
 
5. Quality Action Agent
Responsibilities:
 
Assigns severity.
Recommends accept, rework, quarantine, or stop-line action.
Creates a simulated MES incident.
Sends dashboard alerts.
Records operator feedback.
 
Example:
 
Action: Quarantine Batch B-102Reason: Three critical cracks detected in the last ten productsRecommended check: Inspect press alignment and tool wear
 
Require human approval before simulating a production-line shutdown.
 
The key innovation: a multimodal risk score
Combine signals rather than making separate decisions:
Quality Risk =
    visual anomaly score
  + sensor anomaly score
  + historical similarity
  + defect severity
  + batch-level trend
Example dashboard decision:
Visual defect:             86%
Sensor anomaly:            72%
Historical similarity:     91%
Overall quality risk:      89% — CRITICAL
Recommended action:        Quarantine product and inspect machine
This is easy to explain to judges and makes the system feel complete.
 
Best product features
1. Golden Run Quality Twin
Store a known-good production run containing:
 
Reference product images.
Normal temperature and vibration patterns.
Machine configuration.
Typical cycle time.
 
Every new item is compared against this baseline.
The dashboard can show:
Current product vs Golden Run
Temperature deviation: +7.3°C
Vibration deviation: +18%
Visual anomaly: Surface crack
 
2. Defect Passport
Give every product a digital record:
 
Product ID or QR code.
Inspection image.
Sensor timeline.
Production batch.
Model decision.
Root-cause explanation.
Operator feedback.
Final disposition.
 
This provides traceability and makes MES integration tangible.
 
3. Defect Memory
When a new defect appears, retrieve similar incidents:
 
“This defect is 92% similar to an incident on Machine M-02 last month. The confirmed cause was a worn cutting tool.”
 
For the prototype, similarity can use:
 
Image embeddings.
Defect type.
Sensor conditions.
Machine and product metadata.
 
 
4. Predictive quality mode
Do not only detect defective products. Estimate the risk of the next product being defective.
Example:
 
“The next production cycle has a 74% defect risk due to increasing vibration and temperature drift.”
 
For the demo, use a rolling trend model or straightforward regression. Label it clearly as a risk estimate.
 
5. Human-in-the-loop learning
Allow an operator to select:
 
Correct defect.
False alarm.
Wrong defect type.
Confirm root cause.
Change recommended action.
 
Store this feedback and update future thresholds or the incident memory.
This creates the feedback loop specifically requested in the problem statement.

High-impact demonstration story
Use one short production sequence instead of demonstrating isolated screens.
Scene 1: Normal production
 
Good product images arrive.
Sensor readings remain close to the golden run.
Products receive “Pass” decisions.
 
Scene 2: Gradual process drift
 
Vibration slowly increases.
The Sensor Sentinel identifies an emerging trend.
Predictive quality risk rises, but the system does not yet stop production.
 
Scene 3: Defect appears
 
A scratched or cracked product image arrives.
The Vision Inspector highlights the affected region.
The fusion engine assigns a critical risk score.
 
Scene 4: Root-cause investigation
The system reports:
 
“Probable tool wear. Vibration increased by 22% before the defect appeared. Three similar historical incidents had the same pattern.”
 
Scene 5: Automated response
 
Product is marked “Reject.”
Batch is marked “Inspect.”
A simulated MES incident is created.
Maintenance action is recommended.
 
Scene 6: Operator feedback
 
Operator confirms tool wear.
Incident becomes part of the defect memory.
The dashboard shows that the system learned from the confirmation.
 
This creates a coherent judge-friendly story in about three minutes.
